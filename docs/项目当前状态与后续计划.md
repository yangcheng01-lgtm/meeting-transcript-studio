## 一、项目背景

日常会议、客户拜访和外部访谈中，当前“语音转文字”并不能直接解决信息录入问题，核心瓶颈有三类：

1. **多人交流无法准确归属**：无法稳定回答“谁说了什么”，导致纪要张冠李戴；
2. **外语、口音、专有名词识别质量不稳定**：英语、韩语等外语，以及中文口音、型号、人名、地名、行业术语容易出错；
3. **产出不能直接使用**：已有工具通常只输出一段文字，结论、行动项、负责人、截止时间仍需人工逐句翻听整理。

因此项目真正要解决的不是“能不能转文字”，而是：

> 能否从一段或多段会议录音，形成一份可信、可审改、带人名、带时间戳、可直接用于总结和纪要的结构化产出。

## 三、当前已经完成并验证的能力

### 1. 本地 Speaker 分离

- 模型：`pyannote/speaker-diarization-3.1`；
- 运行环境：`D:\voiceid31`；
- 模型已缓存；
- 已验证 `HF_HUB_OFFLINE=1` 时仍可本地运行；
- 支持已知说话人数，例如两人对话传入 `num_speakers=2`；
- 支持代表片段试听，帮助人工给 `SPEAKER_00` 等标签填写姓名或角色。

### 2. 公司 qwen3-asr Speaker-aware 转写

当前 qwen3-asr 网关实测可以返回文字，但没有返回标准的 native timestamp `segments`。因此采用：

```text
本地 pyannote 先得到 Speaker 时间段
  → 按 Speaker 合并为不超过约 18 秒的音频块
  → 每个音频块调用公司 qwen3-asr
  → 文字块继承 pyannote 的 start/end/speaker
```

已在 120 秒中文对话样本验证：

- pyannote：50 个 Speaker 片段；
- qwen3-asr：36 个 Speaker 文字块；
- 自动对齐：36 段带 Speaker 逐字稿；
- qwen 文字质量优于本地 `faster-whisper small`。

### 3. 多文件会议

已支持一次导入多个音频 / 视频文件：

```text
每个源文件分别转 WAV
  → 按导入顺序拼接
  → 记录每个源文件在总时间轴的 start/end
  → 对拼接后的整场音频统一 Speaker 分离
```

已用 15 秒 + 60 秒两个 WAV 验证为连续 75 秒项目。

### 4. YouTube 导入

已接入 yt-dlp：

- 支持公开 YouTube URL 和 `youtu.be`；
- 默认下载音频，不下载画面；
- 保存 URL、视频 ID、标题、上传者信息；
- 私有、登录、会员、地区限制等不绕过访问控制。

当前尚未用一个真实业务 YouTube URL 完成完整识别回归，属于“功能已接入、真实业务样本待验证”。

## 五、与原始目标相比，当前还存在的 Gap

### P0：必须先解决

#### Gap 1：会议纪要 Agent 还没有真实调用回归

虽然配置 UI、模型列表和纪要 API 已接入，但还没有用实际 API Key 完成：

```text
模型配置
  → 读取模型
  → 调用 meeting-minutes-synthesis-zh
  → 保存会议纪要
```

需要验证：

- 公司网关是否支持 `/v1/models`；
- 公司网关是否支持 `/v1/chat/completions`；
- 模型名是什么；
- 上下文长度是否足够覆盖长会议；
- 失败重试和超时是否合理；
- qwen3-asr 的 API Key 与会议纪要 LLM Key 是否应分开。

#### Gap 2：正式项目还没有完成一份长会议的最终交付

`DT-2026-0001` 已完成 Speaker 分离，但尚未跑完：

```text
1600 个 Speaker 片段
  → qwen3-asr Speaker-aware 分块
  → 带人名逐字稿
  → 会议纪要
```

这是项目从“技术验证”进入“业务可用”的关键验收。

#### Gap 3：长会议的 qwen 请求数量和耗时需要实际测量

120 秒样本约 36 个 qwen 文字块，约耗时 2 分 40 秒。58 分钟会议可能产生大量请求，需要确认：

- 合并规则是否需要优化；
- 是否需要请求级缓存；
- 失败是否能从断点继续；
- API 配额和限流是否能承受；
- 是否需要任务队列。

### P1：进入内网 POC 前必须解决

#### Gap 4：当前任务状态是进程内存，重启会丢

现在使用 Flask 内存字典保存任务状态：

```python
_jobs = {}
```

进程重启后，任务状态和正在运行的任务不可恢复。内网服务器版需要：

```text
Redis / 数据库任务状态
队列
Worker
失败重试
断点续跑
```

#### Gap 5：API Key 当前只在工作台进程内存中

优点是不会落盘；缺点是重启后需要重新填写。服务器版应改为：

- Windows Credential Manager 或 Linux Secret Manager；
- 管理员配置；
- 普通同事不接触 Key；
- ASR Key 和纪要 LLM Key 分离。

#### Gap 6：持久化存储和权限还未建立

当前是本机项目目录和 JSON 文件，尚不具备：

- 用户 / 部门隔离；
- SSO；
- 永久存储策略；
- 备份与恢复；
- 下载 / 导出审计；
- 文件保留和版本记录。

#### Gap 7：多文件顺序和重叠处理还比较简单

已支持多文件串联，但还需要：

- UI 显示文件清单；
- 手动拖拽调整顺序；
- 每个文件单独播放；
- 文件之间重叠检测；
- 重复内容提醒；
- 文件边界显示在最终逐字稿中。

### P2：质量和规模化增强

#### Gap 8：数字、专有名词和行业术语质量

会议纪要必须在输出前做：

- 数字复核；
- 型号、人名、地名词表；
- 常见 ASR 错词校正；
- 低置信度片段回听提示。

#### Gap 9：真正“声纹实名识别”尚未实现

当前是：

```text
Speaker 分离 + 人工命名
```

不是：

```text
跨录音自动识别某个人是谁
```

真正声纹实名需要注册声样、embedding、阈值和 UNKNOWN 策略，另涉及生物特征数据治理。

#### Gap 10：纪要质量需要人工审核闭环

纪要 Skill 已通过文本样本测试，但真实 LLM 输出还需要：

- 事实覆盖率评估；
- 行动项误报率；
- 数字保持率；
- 负责人 / 截止日期幻觉检查；
- 与人工纪要对比。

目标：一台服务器、少量同事、允许排队。

```text

持久化任务表
受控上传

```

验收：

- 5–10 位试用者；
- 同时提交 2–3 个任务可以排队；
- 任务失败可重试；
- 同事看不到其他人的文件；
- 服务重启不会丢项目和历史结果。

### Phase 2：生产化

目标：正式内网工具。

```text

```

目标：让纪要从“可用”变成“可信”。

```text
术语词表
数字复核
低置信度片段
来源时间戳引用

```

### Phase 4：声纹实名识别（可选）

只有在业务需要且完成合规评审后推进：

```text

→ embedding
→ 跨录音匹配

```
